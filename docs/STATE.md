## How we work (decisions)
- **Screens (#566):** a pull request that changes how a screen looks adds or updates that screen's scenario in `tests/screens/screens.mjs` in the same PR (like a test); the `screens` workflow comments the picture and lists skipped scenarios; the agent looks at the picture (from the `screens` branch) before asking for a merge and says what it saw. Desktop Chromium at a phone size, so the owner's iPhone check stays the last step.
- Short replies; Sachin tests on a real iPhone.
- Discuss the design before building a workflow or scheduled job. Run one job by hand first to judge quality and timing, then choose a schedule.
- Merging to main follows the tier policy in `CLAUDE.md`: the agent merges data PRs, UX changes, `jobs/` and `lib/` code, and docs on green `gate`; speed app changes on green `gate` and `perf-ab`; deleting branches or previews is Sachin's call.
- After a UX merge, the agent reads the deploy run and reports it on the issue; the owner checks on the live iPhone, and the item stays `status:waiting-owner` until verified.
- Task locking is claimed atomically via GitHub issue agent labels (`agent:claude` or `agent:gemini` + `status:doing`) and logged in this file.
- **Issue labels (owner, 10 Nov):** one status label per open item. `status:idea` = not decided, needs the owner's go-ahead; `status:ready` = decided, the agent can start; `status:doing` = being worked on and always with `agent:claude` or `agent:gemini` (the lock; a `doing` item without one is reset); `status:waiting-owner` = needs a concrete owner action, and the body's `**What I need from you:**` line says which (decision, merge, phone check). Flow: idea, then ready after the owner's go-ahead, doing, then waiting-owner if an owner check remains, closed when done. A session that finishes or drops an item resets its labels in the same turn. `bash jobs/status.sh` prints a "LABEL PROBLEMS" section that must be empty; fix what it lists before ending a session.
- The multi-agent collaboration protocol is in effect (see `CLAUDE.md` and `docs/ARCHITECTURE.md`).
- Data sources and licences are governed by `build/allowed_sources.json`; changes to that file are owner-merged.
- UI: follow `docs/DESIGN.md`; avoid buttons (plain links or tappable cards); keep mobile and desktop in sync; test the affected area on both sizes, both directions; the full suite runs in CI only.
- Never hand-edit built files (index.html, pilot/index.html, sw.js, api/).
- **Working rules to keep AI usage down (owner asked, 10 Nov):** (1) keep code pull requests few and small (the strict up-to-date rule is off, see "Branch protection", so a merge no longer forces an update-branch and CI re-run on the others); (2) routine bot events (Cloudflare previews, screens, perf-ab comments, check suites for an old head) get no action and no long reply; (3) never poll or sleep-and-check: wait for the PR or check-suite event and read it once; a workflow run with no PR sends no event, so schedule one `send_later` check-in and read it once; (4) before re-running a red check, see whether main fails the same test, and re-run at most once; (5) read only `docs/STATE.md`, the one doc for the task and the files to change, and query data with a one-line script; (6) the platform unsubscribes a session from a pull request when it merges, so only unsubscribe by hand from one that is closed unmerged or abandoned; (7) keep final replies to a sentence or two.
- **Branch protection (owner, 10 Nov):** `main` requires the `gate` check but no longer requires branches to be up to date ("strict" is off; verified by `gh api repos/<repo>/branches/main/protection`). Reason: every merge made every other open pull request "behind" and cost an update-branch plus a ~25 minute CI re-run (the #563 race); no merge queue exists for a personal repository (#593). Consequence for merging: merge a green pull request without updating its branch first; after each merge read the `checks` and `deploy` runs on main for that commit, because a pull request is now tested on the main it branched from, not on the latest main. Update a branch by hand only when two open pull requests touch the same file or the same behaviour (then test both together), and when main goes red after a merge, fix or revert first, before any other merge. If this causes red mains, the fallback is the data train (data jobs open pull requests against a staging branch that lands on main once a day). Only the owner changes this setting; sessions cannot (the proxy refuses it).
- **Labels in use (10 Nov):** exactly ten: `status:idea`, `status:ready`, `status:doing`, `status:waiting-owner`, `theme:data`, `theme:latency`, `theme:photos`, `theme:process`, `agent:claude`, `agent:gemini`. The eleven GitHub default and unused labels were deleted; do not recreate them.
- **No stopgaps (owner, 10 Nov, after #588/#600/#602):** before building, say which layer owns the behaviour (build, data job or app) and put it there; an app-side workaround for something that belongs in the build or data is not shipped "until then". If the proper fix needs a data job or the owner's go-ahead, open the item for that fix and stop. Before merging a behaviour change, list every place it must hold (for search: results list, suggestion dropdown, Species tab) and test each.
- Story batches 25 to 40 places: story at most 60 words, why-it-matters at most 40, every number checked against the research text; park summary one Wikipedia sentence; journeys only where the source text supports a real route; 60% family-level hold rule when promoting.
- Commits and PRs carry the attribution lines given by the session reminder.
- Do not use `pkill -f` / `pgrep -f` (it killed my own shell). Always `git fetch origin +main:refs/remotes/origin/main` before comparing with main. The GitHub GraphQL API is blocked from sessions: use `gh api` REST calls (create PRs with `gh api repos/.../pulls`).
- A new workflow file can only be dispatched after it is on main (or, if it already existed, from its branch).
- A Git branch named `perf` is impossible while any `perf/...` branch exists (today `perf/places-module`; `perf/species-index` is already gone); perf history lives on branch `perf-data`.
- The service worker fetches app/data from the network first, with app-shell fallback for offline navigations; map styles refresh from the network while tiles and media are cached first (up to 1,500 runtime resources). The phone may need two close-and-reopen cycles to show a new deploy.

## What exists (jobs and tools)
Manual workflows: data-about, data-photos, data-largephotos, data-state(s), data-research (`place`: id, list or `next:N[:prefix]`), data-journeys, data-journeyresearch, data-names, data-sync, data-syncall, data-regen, data-promote, data-linktest, data-outlines, data-worldparks, data-speciesphotos, data-after-promote (automatic: a merged `data/promote-*` PR starts data-photos). Scheduled: data-photos (daily 12:17 UTC; one bounded round of up to 120 places), perf (nightly 08:17 UTC; opens the issue "Site got slower" when a metric is over 15% worse), status (daily 11:07 UTC; issue "Project status"). Deploy: pages.yml (its `alert` job opens or updates one issue "Deploy failing" when a deploy job fails and closes it when a deploy succeeds; #326 step 2). The deploy's `live` job runs `build/live_check.py` against the published site: the live `sw.js` and `index.html` must carry the build stamp just built, and `api/places/main/index-world.json`, `cards-world.json`, `api/yellowstone.json`, `api/species/abies-balsamea.json`, `api/search/meta.json` and `api/ties/alabama.json` must answer with real content (retries for 3 minutes); the same check is rehearsed against the staged payload in `verify`. A failure fails the run, so the `alert` job opens the issue (#326 step 3). CI: ci.yml (sharded, with an informational data-quality summary); every pull request that builds also runs `build/pages_payload.py` (the deploy's staging step), so a build the deploy would reject fails before merge (#326 step 1).
- Perf harness: `tests/perf/perf.mjs`; history and latest report live on `perf-data` (`history.json`, `latest.md`). Phone profile = 4x CPU, 1.6 Mbps, 150 ms. It reports page/map/tap medians, cold/warm route readiness, selected-species response time, resource classes, Places load stages, and long tasks; observational readiness/stage results do not raise regression warnings. Each sample uses a fresh browser context with service workers blocked, but the browser process and origin/CDN may be warm.
- Performance measurement rule: compare profiles on GitHub Actions using the same workflow, build, and profile conditions; do not overlap performance runs. These are small, descriptive samples, not stable tail estimates or proof of end-to-end improvement. Fresh browser contexts block service workers, but the browser process and origin/CDN may be warm.
- Perf measurements (initial Places load, route readiness, Explore profiling and layout cache, payload audit) are in `docs/history/2026-11-state-log.md`.
- Photos: the app normalizes legacy `photos/places/places.json` and `photos/species.json` into an entity-keyed candidate registry in memory. Place images retain their local files and now carry measured MIME type, dimensions, and SHA-256; species keeps the old list shape for compatibility, preserves absolute Wikimedia URLs as-is, and serves existing 120px thumbnail variants for relative paths. Candidate fallback is local-first, then other eligible Wikimedia candidates; pending or rejected candidates are never displayed. Legacy species photos remain available with their current Wikipedia attribution until full author/licence records are reviewed. The 1 Nov species-photo metadata audit (`docs/history/2026-11-01-species-photo-metadata-audit.md`, a snapshot: it found 15 of 4,802 with their own record) is out of date; `photos/species_metadata.json` now has 4,773 entries for 4,777 pictures.
- Photo jobs open human-reviewable PRs. Wikimedia is the default source; GBIF observation photos (CC0 and CC BY, named author, no iNaturalist, no specimen sheets) are the one other source, approved by the owner in #421 B2 / #511 (credit page `www.gbif.org`, label "GBIF" on the credit line). Place and species no-match entries expire after 180 days; transient request failures are not negatively cached, and Wikimedia throttling retries are bounded. Actions validation checks local image signatures, dimensions, hashes, HTTPS credits, and allowed species image hosts. Species aliases continue to use the canonical manifest tuple (for example, Bottlenose dolphin -> Common bottlenose dolphin); no-match titles are recorded in `photos/species_missing.json`.
- Outlines: `data/outlines/<id>.json` (PAD-US, then Wikidata/Commons, then OpenStreetMap; `bounds_more.py` drops a match whose box is far from the place).

The stored place photo list (`photos/places/places.json`, 117 KB gz) is fetched at that release too, not at start (#397, PR open, perf-ab pending).
