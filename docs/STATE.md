## How we work (decisions)
- Short replies; Sachin tests on a real iPhone.
- Discuss the design before building a workflow or scheduled job. Run one job by hand first to judge quality and timing, then choose a schedule.
- Heavy web pulls run as GitHub Actions jobs, triggered and left in the background. Jobs never merge; they open one pull request.
- Merging to main, deleting branches and closing PRs are Sachin's call. "Yes to N" / "Go ahead" counts as approval of the PRs I listed. Wait for green CI before merging to main.
- UI: follow `docs/DESIGN.md`; avoid buttons (plain links or tappable cards); keep mobile and desktop in sync; test the affected area on both sizes, both directions; the full suite runs in CI only.
- Never hand-edit built files (index.html, pilot/index.html, sw.js, webs/).
- Story batches 25 to 40 places: story at most 60 words, why-it-matters at most 40, every number checked against the research text; park summary one Wikipedia sentence; journeys only where the source text supports a real route; 60% family-level hold rule when promoting.
- Commits and PRs carry the attribution lines given by the session reminder.
- Do not use `pkill -f` / `pgrep -f` (it killed my own shell). Always `git fetch origin +main:refs/remotes/origin/main` before comparing with main. The GitHub GraphQL API is blocked from sessions: use `gh api` REST calls (create PRs with `gh api repos/.../pulls`).
- A new workflow file can only be dispatched after it is on main (or, if it already existed, from its branch).
- A Git branch named `perf` is impossible while `perf/species-index` exists; perf history lives on branch `perf-data`.
- The service worker fetches app/data from the network first, with app-shell fallback for offline navigations; map styles refresh from the network while tiles and media are cached first (up to 1,500 runtime resources). The phone may need two close-and-reopen cycles to show a new deploy.

## What exists (jobs and tools)
Manual workflows: data-about, data-photos, data-state(s), data-research (`place`: id, list or `next:N[:prefix]`), data-journeys, data-journeyresearch, data-names, data-sync, data-syncall, data-regen, data-promote, data-linktest, data-outlines, data-worldparks, data-speciesphotos, data-after-promote (automatic: a merged `data/promote-*` PR starts data-photos). Scheduled: data-photos (daily 12:17 UTC; one bounded round of up to 120 places), perf (nightly 08:17 UTC; opens the issue "Site got slower" when a metric is over 15% worse), status (daily 11:07 UTC; issue "Project status"). Deploy: pages.yml. CI: ci.yml (sharded, with an informational data-quality summary).
- Perf harness: `tests/perf/perf.mjs`; history and latest report live on `perf-data` (`history.json`, `latest.md`). Phone profile = 4x CPU, 1.6 Mbps, 150 ms. It reports page/map/tap medians, cold/warm route readiness, selected-species response time, resource classes, Places load stages, and long tasks; observational readiness/stage results do not raise regression warnings. Each sample uses a fresh browser context with service workers blocked, but the browser process and origin/CDN may be warm.
- Performance measurement rule: compare profiles on GitHub Actions using the same workflow, build, and profile conditions; do not overlap performance runs. These are small, descriptive samples, not stable tail estimates or proof of end-to-end improvement. Fresh browser contexts block service workers, but the browser process and origin/CDN may be warm.
- Initial Places load: PR [#169](https://github.com/sachinwankhede/connected-earth/pull/169) merged 2026-11-01 and added observational stage instrumentation, not an optimization. Its five-sample-per-profile Actions baseline reported map-loaded p50/p95 of 7.5/17.2 s phone-like and 2.1/2.4 s desktop; phone long-task blocking was 1.23/3.77 s. Treat stage durations as measured only where the instrumentation explicitly measures them; other durations are inferred. With n=5, p95 is especially unstable. System Chrome was used because the local Playwright browser download stalled.
- Places sheet soft-fade scroll-height reads are coalesced to at most one animation frame; this reduces redundant layout reads but is not a measured end-to-end latency improvement.
- Route readiness baseline: GitHub Actions run [41267793957](https://github.com/sachinwankhede/connected-earth/actions/runs/41267793957) measured place-route-ready p50 cold/warm of 340/213 ms phone and 56/64 ms desktop; food-web was 465/345 ms phone and 100/195 ms desktop. Cold route loads fetched about 5 KB of web data; warm loads made no web-data request. These are route-ready/tap timings, not internal fetch/parse/DOM/map breakdowns. Warm was not uniformly faster; this does not establish a caching issue.
- Explore profiling: run [41268973422](https://github.com/sachinwankhede/connected-earth/actions/runs/41268973422) used five samples per phase/profile. Warm Explore made zero web-data fetches but still ran 120 synchronous graph ticks (p50 tick time 85.8 ms phone / 18.3 ms desktop; warm total setup 182.8/108.1 ms). Temporary profiling instrumentation was removed after measurement. This isolated repeat graph work as a candidate, not a proven end-to-end bottleneck.
- Explore graph layouts are cached in memory by ecosystem content, mode/environment, and viewport geometry; the cache holds at most 12 layouts. Matching warm reopens skip all 120 synchronous layout ticks; misses retain the cold path. PR [#170](https://github.com/sachinwankhede/connected-earth/pull/170) merged 2026-11-01. Actions run [41271555947](https://github.com/sachinwankhede/connected-earth/actions/runs/41271555947) confirmed zero warm ticks; cold tick p50 was 118.3 ms phone / 64.0 ms desktop, and warm tick p50/p95 was 0/0.1 ms on both profiles. Other route-ready/setup timings varied, so do not claim a reliable end-to-end speedup. Test cold and warm opens, ecosystem switches, and viewport resizing; invalidate reuse when graph content/configuration or viewport changes.
- Payload audit on main: built index HTML is about 2.81 MB raw / 699 KB gzip. Candidate experiments are route-splitting D3 (~92 KB gzip estimate) and deferring the place-photo manifest (~115 KB gzip estimate); both carry offline/navigation risks and have no demonstrated latency gain. Deferring state geometry remains parked: it breaks first-visit offline behavior unless precached, which negates the transfer savings.
- Photos: the app normalizes legacy `photos/places/places.json` and `photos/species.json` into an entity-keyed candidate registry in memory. Place images retain their local files and now carry measured MIME type, dimensions, and SHA-256; species keeps the old list shape for compatibility, preserves absolute Wikimedia URLs as-is, and serves existing 120px thumbnail variants for relative paths. Candidate fallback is local-first, then other eligible Wikimedia candidates; pending or rejected candidates are never displayed. Legacy species photos remain available with their current Wikipedia attribution until full author/licence records are reviewed. The 2026-11 species-photo metadata audit verified 15 exact Commons files into `photos/species_metadata.json`; the remaining 4,787 have no new per-file credits and are classified in `docs/species-photo-metadata.md`.
- Photo jobs open human-reviewable PRs and never add non-Wikimedia providers. Place and species no-match entries expire after 180 days; transient request failures are not negatively cached, and Wikimedia throttling retries are bounded. Actions validation checks local image signatures, dimensions, hashes, HTTPS credits, and allowed species image hosts. Species aliases continue to use the canonical manifest tuple (for example, Bottlenose dolphin -> Common bottlenose dolphin); no-match titles are recorded in `photos/species_missing.json`.
- Outlines: `data/outlines/<id>.json` (PAD-US, then Wikidata/Commons, then OpenStreetMap; `bounds_more.py` drops a match whose box is far from the place).
- Size budgets in `build/budget.py` (index 3.6 MB, pilot 4.2, species 4, webs 25, outlines 20).
- Place pictures wait for the map (map drawn, a touch, 9 s, or a link to a place). Food-web species photos use smaller thumbnail variants and native lazy loading.
- After adding or promoting places run `python3 build/species.py pack`. A data branch that clashes with main only on `data/species.json` or `data-auto/order.json`: use data-sync.

## Latency plan (started 2026-11-01)
- **Design decided 2026-11-01:** code and data are separate and data loads in pieces; see `docs/ARCHITECTURE.md` (steps are items #227, #228, #229; D3 on demand is #186). Offline for all places is not required; search may be briefly unavailable after launch.
- Findings (phone profile, five-sample medians from `perf-data` `latest.md`): first paint 0.4 s; app data, cards and map style all ready at 5.2 s (same moment as DOM interactive); first tile 5.7 s; map loaded 7.4 s; first photo decoded 7.9 s; long tasks block the main thread for about 1.3 s.
- Why: the built page is one file, 699 KB gzip, so at 1.6 Mbps the download alone is about 3.5 s. Of it, roughly 376 KB gzip is our own code and data (places 157 KB, species table 61 KB, state/country geometry 72 KB, app 64 KB, land 17 KB) and about 307 KB is MapLibre plus D3 (D3 about 92 KB). The per-place detail (`webs/`, 12.8 MB raw) already loads on demand; the weak spots are card text for all 1,272 places and the species table loading before first paint, and everything inlined in one file that is re-sent on every deploy.
- Rough, unmeasured estimates of what each could save on the phone profile: defer D3 about 0.5 s; slim places index about 0.5 s; species table on demand about 0.3 s; earlier connection to the tile hosts perhaps 0.5 to 1 s. Together about 1.5 to 2 s of 7.4 s.
- Gap: the perf harness blocks service workers and always loads as a first visit. The service worker fetches the page with `cache: "no-cache"` on every open, so a returning visit is a re-check or a re-download; which one is not measured yet. `tests/perf/perf.mjs` now has an observational returning-visit section (service worker on, document status and bytes on the wire).
- Merged 2026-11-01 (each compared with main by `perf-ab` on one runner, phone profile): lazy species lists and ties (#178); species lists in `webs/species-index.json`, loaded after the map (#179: page loaded -16%, map drawn -10%); world outline and name shown at once from the page itself, removed when the map is idle (#209: no timing change, about 19 KB more, removes the empty screen); our own font files in `fonts/` (Bricolage Grotesque and Instrument Sans, Latin subset, about 103 KB) instead of Google Fonts, and the separate mono font dropped, the small uppercase labels use the body font (#213: page loaded -21% phone / -32% desktop, 16 metrics better, none worse); the map library moved after the app script, so the places list draws before the map code has arrived (#211: list ready 4.5 s to 3.0 s, map style ready about 0.7 s later; the place-picture release hooks the map when it is created).
- Tried, no gain: asking for the food-web preview pictures in groups, top level first (#204): the last picture still arrived at about 4.5 s after the tap. Fonts loaded in the background (#205): superseded by self-hosted fonts. Comparing old commits with perf-ab fails: old commits lack files the build needs; the nightly history (page loaded 5.1 to 6.2 s, no trend) showed that the "Site got slower" warnings were runner noise.
- Findings: the empty screen at start came from one big file: the page cannot run until most of it has arrived. Place pictures: the first arrives about 1.2 s and the last about 4.5 s after the tap (phone profile); the food-web preview draws one picture per species and SVG images are not lazy. Offline note: the species index is cached by the service worker when first fetched.
