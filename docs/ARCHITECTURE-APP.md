# Architecture: the app

How the app loads and uses data, its source files, chunks and the first-view budget. Part of the design in `docs/ARCHITECTURE.md`; sections are moved word for word from it.

## What the app does with "all places" (audit for #313 step 4b, 3 Nov)
`ECOS` (the full list of loaded places) is read in about 30 places of the app source (`src/app/`). Loading one region at a time only works if each use is served by something smaller. The uses fall into six groups:

| Group | Where (functions) | What it really needs | Served by |
|---|---|---|---|
| A. Map dots and fitting | `ecoFC`, `flagFC`, visible-in-view count, `mapFit`, fit-to-region | id, lat, lon, kind, flags, level, and region membership (`inRegion`: continents, countries, states) | positions file, **if it also carries region membership** (today it has id, short, lat, lon, kind, flags only) |
| B. Counts and browse lists | continent, country, state browse rows, per-kind counts, "N results" | counts per region and kind, with park, local and query filters applied | `counts.json` for the plain case; positions for any filtered case; search hits for a query |
| C. Card list and paging | the list built from `ECOS.filter(inRegion)`, card DOM, photo wanting | the cards of the region being listed | the shard of that region, loaded when the list opens |
| D. Near me | `nearMe` | positions of every place to rank, then cards of the nearest five | positions, then 5 cards by id |
| E. Species overlap | related places on a place page, the same species in other places, the species ties graph, the species-to-places lookup | for each species, which places hold it | **not placeable by region.** Needs the precomputed related-places (#252) and species-to-places (#253) data; today it scans every place's species list from the 134 KB gz species index |
| F. Start-up loops | species filling for all places, place dropdown options, `ECO_BY` fill, the old search-text fallback, map label de-duplication (`short` of every place), test hook `ecoIds` | mostly ids and short names | positions (id, short); species and search text come with the index and search files |

Design rules this gives (to be decided before step 4b is coded):
1. **A light directory of all places stays in memory** (positions plus region membership, about 12 to 15 KB gz). Groups A, B, D and F read it. It replaces `ECOS` for everything except card text.
2. **Cards are fetched by id**, through one function that finds the shard (region key stored in the directory) and returns a promise. Every place page, peek, card list and Near me row goes through it. This is the "not yet" guard of step 3 made the normal path, not a patch.
3. **Positions must carry region membership** (or the shard key plus enough to answer `inRegion`). This is a build change in `split_regions` and the first thing to do.
4. **Group E is a blocker, not a detail.** Region loading does not remove the scan; it makes it wrong, because a place's neighbours may live in a region that has not loaded. #252 and #253 must land first, so the app reads the answer and no longer computes it.
5. **The species index (134 KB gz) is larger than all place files together** and is only needed for group E and species search. After #252/#253 it can be dropped from start-up.
6. Tests that call `__M.showPlace(id)` or open places by link must wait for the card, so the test helpers need a "place ready" wait.

## Map first tiles (#244)
The satellite style has two raster layers on the same tile address. `sat0` counts the 256 px pictures as 512 and is capped at zoom 1, so the opening world view on a phone (zoom 0.6) asks for about 4 tiles instead of about 12; `sat` (normal detail) exists only from zoom 1 and fades in over `sat0` between zoom 1 and 1.2. A layer outside its zoom range asks for no tiles. The cost is a softer picture before the first zoom-in. On a phone the map is created at its fit zoom (0.6) so no detailed tiles are asked for before the fit.

## Data module in the app (#241)
`Data` in `src/app/data.js` is the one place that knows where the app's data files are and how to read them: `Data.json(url, missing)` (a 404 gives `missing` when given, any other failure rejects) plus named calls. Step 1 moved the species description (`Data.species`), the park outline (`Data.bounds`) and the US state outlines (`Data.states`) behind it with the same URLs and the same error behaviour. Step 2 (done): a place's own file (`Data.place`), search files (`Data.search`), ties (`Data.ties`) and species-to-places (`Data.speciesPlaces`); the search lookup test loads `Data` from the built page. The head loader for the world places stays in the head (it must start before the app script). **Journeys (#377):** the build writes the journeys with the couple and source settings to `api/journeys/main.json` and `pilot.json` (no longer inlined in the page as `var DATA`); the head loader fetches the file in parallel with the world places (`window.__JOURNEYS`) and the app starts when both have arrived, so the synchronous reads of `CROSS`, `COUPLE` and `SRC` stay valid. If the file cannot be loaded the app starts with no journeys. The file is precached by the service worker and is on the first-view list. The head loader's journeys line is whitelisted in `tests/data/data_access.test.mjs`. Not a `Data` call: the head owns the one fetch because the app cannot start before it. A test can now replace the journeys with a request route, like the fixture places. Step 3 (done): the species pictures (`Data.pictures`) and the stored place photos (`Data.placePhotos`, `{}` when missing), fetched when the photos are released (map drawn, a touch, 9 s, or a link to a place) and not at start (#397); cards and the place page ask for pictures through `M.wantPhoto`, which holds them until the list has arrived, and `tests/data/data_access.test.mjs`, which fails if `fetch(` appears in the app outside `Data` and the head loader. A new data read goes into `Data` as a named call.


## First-view weight budget (#369)
`build/budget.py` (run on every app and data pull request) also calls `build/firstview.py`. It blocks on two things that do not jitter: the gzip size (level 9, Pages serves gzip only) of the files a phone fetches before the first draw (the page, the map library, the world places `index-world.json` and `cards-world.json`, and since #377 the journeys file `api/journeys/main.json`), and the outside hosts the page loads from (map tiles, glyphs, satellite, elevation; plain `<a>` links are not loads). Limits: 404,000 gzip bytes (about 2% above 396,072 on 4 Nov 2026, measured after #398 removed the unused `LAND` literal, 14.7 KB gz from the page; it was 418,000 above 410,781) and the three hosts in `HOSTS_ALLOWED`. Raising a limit or adding a host is a deliberate edit in `build/firstview.py`, in the pull request that needs it. Request count and timings are not blocked on (perf-ab reports them; timings swing ±20% with no code change). `tests/data/firstview_budget_test.py` pins the rules.

## Loading tiers and fetch priority (#718; owner 12 Nov asked for a guideline, the wording is the agent's)
Anything that loads after the first view belongs to one of four tiers. A new loader says its tier in a comment beside it, and a piece that does not fit a tier is not added without asking the owner.

1. **First view.** In the page: what the first paint and the first tap need. Governed by the first-view budget (`build/firstview.py`, Brotli total).
2. **After the map is drawn.** Small things that make the first tap feel instant (the pictures of the places in view). Start when the map has settled (`idle`), at normal priority.
3. **Quiet time.** Things people often reach next but do not need yet (d3, the state outlines, the Species tab file, the attention pulse). Rules: start only after the map has drawn; low priority (`fetchpriority="low"` on a script, `priority: "low"` on `fetch`, or a `prefetch` link), so tiles and pictures win; fetch without running where the browser allows; skip when the phone asks to save data (`navigator.connection.saveData`) or reports a slow connection (`effectiveType` of `slow-2g` or `2g`); do not start a new one after the first touch or key press (the touch loads what it needs); never block a tap.
4. **On demand.** Loaded when the person asks (a place's web, a species page, the Species tab if not yet fetched). Normal or high priority, and a short loading state; nothing here is prefetched without a measured reason.

Before merging a new loader: say its tier and its bytes (Brotli) in the pull request; a quiet-time piece over about 50 KB Brotli also needs a `perf-ab` run with `nav=1` and its download total reported. The usual rule stands: first paint, map drawn and tap times more than 15% worse (and more than 20 ms) stop the merge and go to the owner. Under `#stub` (the tests) no tier 3 piece loads, so the request counts the tests check stay true.

**Where the existing pieces sit today.** Pictures released at map idle or first touch: tier 2. The state outlines (fetched in the quiet time after the map), and d3, the Species tab file and the outlines again fetched by the service worker after install (`LATER_FILES` in `src/sw.template.js`): tier 3, the service worker's fetches off the page's own network queue. The per-region counts at the first touch: tier 4. A place's web, a species page: tier 4. The pulse chunk (#717) is tier 3 but does not yet set low priority or check data-saver mode; that is a follow-up.

## Chip counts from the build (#261, step 1, 4 Nov 2026)
`Data.counts()` reads `api/places/<main|pilot>/counts.json` (written by the build since #313: per region `c:`, `k:`, `s:` and `w`, places as [world, local], per kind and park). The chip counts in `chipsHTML` (`src/app/map-view.js`) use it when it has arrived and the file can answer (no search text; a kind or parks filter alone; the local button only once the local places are in); otherwise they count the places in memory as before. The file is fetched at the first touch, not at start, so the first view makes no extra request. Step 2 (4 Nov 2026): which chips appear (continents at the world view, countries of a continent, US states) also comes from the file when it can answer: the keys of `counts.json` with a count above zero under the current filters (countries only where `M.countryBy` puts them in the viewed continent), else the old scan (`scanKeys`, `fileKeys`, `chipKeys` in `src/app/map-view.js`). Checked on the built files for main and pilot: the file's continent, country and state keys equal those of the places, every country lies in a continent of its place, and states occur only in US places. `tests/app/counts.test.mjs` checks that file and scan agree for every region in several filter states (`M.countsCheck`) and for the chip lists at the world, continent, country and state views (`M.listsCheck`). Today both answers are the same because all places are in memory; the file is what step 4b of #313 will rely on.

## The address (hash) and Back (#412)
`hashState()` in `src/app/map-state.js` writes one address for the screen: `s=<text>` (the search box, `encodeURIComponent`, then the whole hash goes through `encodeURI`) first, then at most one of `j=` (journey), `pg=` (place), `e=` (food web), `p=` (peeked place) or `r=continent|country|state:<name>` (the region; it takes the rest of the address, so `s=` must come before it). `applyHash()` reads it on load and on `hashchange`: `s=` sets the box and runs the search (`runSearch()` in `cards.js`, also used when typing); an address with no `s=` clears a search; an address with no place while a place page is open closes it. History: the address is normally replaced as you go (`replaceState`). Two things add one entry (`M.pushNext`, `history.pushState`): the first letter typed (or a species filter that starts from no search) and a place opened from a search; the place's entry carries `history.state.sp`, and the page's own "‹ Places" link then calls `history.back()` instead of replacing it, so Back, the link and the phone's swipe all behave the same. What the address itself opens (`M.fromHash`, set for the whole start-up, first draw included) never adds an entry and never wipes the entry's state. Known small wart: after Clear, one Back press changes nothing visible (it returns to the entry before the search, which looks the same).

## The species page (#420)
`showSpecies(sid)` (`src/app/species.js`) draws the species page into `#pview` (with `M.sid` set, `M.pid` null); the address is `sp=<latin slug>` after any `s=`, Back and the history marker work as for a place (a page opened from a search is its own entry; `closeSpecies()` is Back then). The page needs one file, `api/species/<id>.json` (read through `Data.species`): the build now writes it for every species of the places, not only those with a description: `l` Latin name, `n` usual name, `tl` level, `ic` icon, `t` description (when there is one), `ph` and `phm` the hosted picture entry and its credit (when there is one; the same shape as a place file's `ph`/`phm`, registered under the Latin name). The old sheet reads only `t`. The folder is 2.0 MB for about 5,000 files, each fetched alone when a sheet or page opens (`ABOUT_MAX` is 2.4 MB). A missing file gives a page with the name made from the address. Step 2: once the file is read, `sppPlaces(latin)` (the same file the map filter uses; it now lists single-place species too, +100 KB over all buckets, largest bucket 35.9 KB of the 40 KB budget) gives the places: the first ten as `.pj` rows (anchors, picture through `pWant` with `eco` = the species id) under "Found in N places", and a "Show them on the map" link that runs `speciesMap`. A row opens the place as its own history step, so Back returns to the species page.

Step 3 (entry points): the dropdown's species row calls `showSpecies` (Back is "‹ Search" and returns to the typed search); the species sheet's "Also found in N other places" header carries a link "Species page ›" (it replaced that header's "Show on the map", which is on the page now): it sets `M.pushNext`, passes the place's name as the back label (`M.spFrom`) and Back returns to the graph. "Show on the map" is on the page only.

## The Species tab files (#422 step 1)
The build writes `api/species-tab/` (main) and `api/species-tab-pilot/`: `top.json` (the 60 species found in the most places), `groups.json` (`[key, label, species, pages]` for mammals, birds, reptiles, amphibians, fish, insects, other animals, plants, fungi, algae and others; a group with no species is left out) and `g-<key>-<n>.json` (a page of 250 rows of a group). A row is `[Latin name, usual name, number of places, hosted picture file or 0]`, most places first, then by name; the number is the species' places in that page set (the same as `api/species-places/`). The group comes from the taxonomy (`data/species/taxonomy.json`, kingdom and class: `species_group` in `build/build.py`; a species with no record is in "Algae and others"). A species row of the suggestion files `s-<xx>.json` is `[Latin name, usual name, places, hosted picture file or 0]`, so the dropdown and the tab's search show the picture without loading the list of every picture (#443). `api/species/<id>.json` also carries `g` (group key as in `api/species-tab/groups.json`), `od` (order) and `fa` (family) from the taxonomy; a species with no taxonomy record has none of the three. `ea` and `eb` list what it eats and what eats it (`species_diet` in `build/build.py`; up to four rows of `[Latin name, usual name, number of places, picture file or 0]` each, from the food links of the places, a link [food, eater] counted once per place; `api/species/` is about 3.1 MB, budget 5.2 MB). `rl` lists up to five other species of the same family (`species_related`; same row form; `api/species/` budget 6.4 MB). `pl` = 1 says a 400 px copy of the same picture is in `photos/species-lg/` (listed in `photos/species_large.json`); the page loads it from there. The species page itself is built by the same lazy chunk (`show(sid)`; the first view's `showSpecies` only does what must happen at once: the address, hiding the other views, the placeholder), so the page can grow without the first view's size budget (#445). The Species tab reads `top.json` and `groups.json` when it opens and a group's pages one at a time. Budgets: 30 KB per file, 800 KB per folder (today 16 KB and 282 KB).

## App code outside the first view: chunks (#422 step 2)
The first view has little size budget left, so the Species tab's code is `src/chunks/species-tab.js`, not part of the page. The build copies it to `species-tab-<hash>.js` (hash of its text; `__TABVER__` in the page and in `sw.js`, which fetches it after install like d3; the deploy copies `species-tab-*.js`; the file is not committed). `withSpeciesTab()` (`src/app/cards.js`) loads it the first time the tab opens and calls the function the file registers in `window.__chunk["species-tab"]` with one object `A`: `Data`, `PhotoRegistry`, `esc`, the row icons and `go(latin)` (opens a species page, Back is "‹ Species"). A chunk reaches the page only through `A` and reads data only through `A.Data` (`Data.speciesTab`). The tab is a third state of `setTab` (`tab-s` on `#sbody` hides the places list, `#sptab` holds the tab); first view +609 bytes gz for the tab button, the loader and the CSS. Groups and paging (step 3) live in the chunk; search on the tab (step 4) asks the page through `A.find(text)` (the suggestion files' species rows, up to 40, ranked as the dropdown ranks them) and listens to the box itself; on the tab `sugShow` passes only the species to the dropdown (+108 bytes gz in the first view).

## The result header, the why line and the chip (#425)
`qHead()` (`suggest.js`, called from `renderView`, only when the query or the busy flag or the chip changes) asks `sugPick` on the already cached suggestion file for the typed text: a rank-0 row is an exact species or place and fills `#qhead`. For a species it also reads `sppPlaces(latin)` (the file the map filter uses) and `whyLines()` writes "Has <name>" on the cards of those places. `speciesMap` sets `M.chip` to the query: the header then reads "Places with <name> ✕" and the ✕ clicks the box's Clear. No new data file; a why line for text that is not an exact species needs the kind of the matching word in the word files (not built: it would add to every word file for a line that is only sometimes right).

## Search draws once and says what is true (#414)
Typing runs `runSearch()` (`cards.js`): the first letter and Clear at once, letters typed within 120 ms of the last run wait for the end of the burst (`M.qT`). It does not draw a query: `searchFor()` (`data.js`) sets `FL.busy`, keeps the list on the screen as it was, and draws once when the index has answered (`FL.hits`, or the card text when the index could not be had, then `FL.limited`). After 250 ms without an answer the line under the box reads "Searching…" (`M.busyT`); `renderView()` (`map-state.js`) never shows the nothing-found line while `FL.busy` (it says what was searched, with a Clear link `#eclr`; inside a region the line keeps the query and the region). The local places start loading when the box is first focused. `M.searched` (the query the list answers) and `M.hitsN` (index hits, -1 when the index was not used) are what the tests wait for.
