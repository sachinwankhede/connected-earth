# Architecture: build, tests, CI and deploy

Tests and CI by kind of change, deployment, the perf gate, merge tiers and source governance. Part of the design in `docs/ARCHITECTURE.md`; sections are moved word for word from it.

## Tests and CI by kind of change (added 2026-11-02, items #269 and #272)
Tests live in `tests/app/` (browser and app code), `tests/data/` (data files, no browser), `tests/jobs/` (job scripts and the CI rules) and `tests/perf/` (speed harness). `build/ci_changes.py` decides what a change needs: app changes run everything; data changes run validation, the pack check, build, size budgets, data tests and one smoke test; job changes run only the job self-tests; docs, notes, data-job workflows and job state files run nothing. The `gate` job always runs and is the one check to require.

**Fixture places for browser tests (#292).** `tests/fixtures/places/` holds small made-up places (Testland, with a web over all five levels, and Testwater, related to it). A test asks for them with `H.open(..., { fixtures: true })`: the helper adds them to the world places and answers their files from the fixture folder, so the test checks the app's behaviour and not what the real data says today. Everything else on the page is unchanged. A test that needs one place with certain features should use a fixture instead of 'yellowstone'; move tests over one group per pull request. A test that runs its own file server uses `H.fixtureList(path, builtText)` (the world index and cards with the fixtures added) and `H.fixturePlace(path)` (a copy of a fixture's place file); `speciesphotos.test.mjs` does. Tests whose point is a real stored photo (`photos.test.mjs`, `photohold.test.mjs`) stay on the real data on purpose. Photo mocking lives in `tests/app/mockphotos.mjs`: `mockPhotos(page)` answers every photo request for the whole page, `mockSpeciesPictures(page, ph)` answers the species picture list with exactly the entries given (journey tests). The suites that run their own file server (`speciesphotos`, `photohold`, `requests`) control the picture list per test on purpose and keep their own server code. Testland's coyote is named by an alias (`wiki` 'Coyote alias', `canonicalWiki` 'Coyote canonical') for the alias picture test.

## Dual Deployment & Edge Delivery Architecture (Cloudflare + GitHub Pages)
The application deploys to two environments from the same build output (`dist/pages` generated by `python3 build/pages_payload.py`):
1. **Cloudflare Pages**: Published at `https://connected-earth-5ps.pages.dev/`. Connected via Cloudflare's GitHub integration (the Cloudflare Workers and Pages GitHub App), building on commit pushes and generating isolated preview deployments for pull requests (`https://<branch>.connected-earth-5ps.pages.dev/` and `https://<commit-prefix>.connected-earth-5ps.pages.dev/`).
2. **GitHub Pages**: Published at `https://sachinwankhede.github.io/connected-earth/`. Deployed via GitHub Actions (`pages.yml`).
Both environments deploy identical staged payloads from `dist/pages` without modifying source or runtime code.

### Split payloads (item #692)
A Cloudflare Pages project holds at most 20,000 files in a deployment; the whole site is about 21,100. `python3 build/pages_payload.py --mode <all|app|species>` stages the same files as one payload (`all`, in `dist/pages`: GitHub Pages and the default), without the species files (`app`, `dist/pages`), or only the species files (`species`, `dist/pages-species`, with a `_headers` file for cross-origin reading and caching). The species files are `api/species/`, `photos/species-md/` and `photos/species-lg/`. The environment variable `SPECIES_BASE` (an https address) at build time makes the app read them from there (`__SPECIES_ROOT__`, `__SPECIES_PHOTOS__` in `src/app/data.js` and `src/app/photos.js`; the service worker caches that host like the other photo hosts). Without it the built files are byte for byte what they were before. Cloudflare project 1: build command `SPECIES_BASE=<species address> npm run build && python3 build/pages_payload.py --mode app`, output `dist/pages`. Cloudflare project 2 (species): build command `npm run build && python3 build/pages_payload.py --mode species`, output `dist/pages-species`. `tests/data/pages_split_test.py` checks the split.

## Automated Performance Gate & Regression Benchmarking (perf-ab)
Performance is an architectural pillar for Connected Earth's global mobile-first experience. To safeguard latency without blocking routine development on runner noise:
- **Comparative A/B Benchmarking (`perf-ab`):** For app-code PRs (`app == true` according to `build/ci_changes.py`), the agent dispatches `perf-ab` and reads the comparison table before merging. Docs, data, and job-script pull requests skip it to conserve CI runner minutes.
- **Strict A/B Comparative Testing:** Rather than relying on volatile absolute timings, `perf-ab` builds both baseline (`origin/main`, side A) and the PR branch (side B) on the same runner machine under identical conditions, alternating execution order across multiple iterations (default 5 runs per side) on both the phone profile (4x CPU slowdown, 1.6 Mbps download, 150 ms RTT) and desktop profile.
- **Single 15% Regression Threshold:** Aligned with `docs/STATE.md` and `tests/perf/compare.mjs`, regressions are evaluated against a single 15% threshold (flagging metrics that degrade by > 15% and > 20 ms / KB).
- **Noise-Tolerant Warning Gate:** Because shared virtualized CI runners experience transient timing jitter, the gate outputs comprehensive comparison tables and flags regressions as explicit PR warnings for human or agent inspection, rather than blindly failing the build on a single noisy run.

## Pull Request Merge Policy & Quality Tiers
Nothing merges automatically because GitHub's "Allow auto-merge" is disabled. The agent merges qualifying pull requests across designated tiers once automated checks pass:

1. **The Agent Merges on Green Gate:**
   - **Data Pull Requests:** Opened by automated data jobs; each data PR lists its sources and licences in the body along with the 10-item spot check required by `docs/PROMOTION.md`. The owner's workflow run approval (`action_required`) serves as standing approval to merge once CI `gate` is green.
   - **UX Changes:** CSS in `src/app/style.css`, layout shells in `src/app.html`, cards, sheets, typography, search rows, and gestures. The agent runs `perf-ab` before merging (informational; blocks only on >15% slowdown). The agent merges once `gate` passes, reads the `deploy` run, and posts the deployment link on the issue item. The owner tests on their physical iPhone on production; the item remains `status:waiting-owner` until verified. (Cloudflare edge previews remain available as an optional pre-merge testing tool).
   - **Job Scripts & Shared Libraries (`jobs/`, `lib/`):** Requires a unit test in the pull request and must pass the source whitelist gate (`tests/jobs/allowed_sources_test.py`). All downloads route through `lib/fetch.py` which refuses unlisted hosts at run time.
   - **Docs-Only Changes:** Updates to documentation and markdown files (except owner-merged governance files).

2. **The Agent Merges on Green Gate and `perf-ab`:**
   - **Speed & Latency App Code:** Changes affecting runtime speed, bundle payload, or performance budgets (`app == true` according to `build/ci_changes.py`, such as `src/app/data.js`, `build/build.py`, `build/pages_payload.py`, `sw.js`, or bundle chunking). The agent dispatches `perf-ab`, reads the comparison table, and merges if there is no regression > 15% (and > 20 ms / KB).

3. **Stays Owner-Merged:**
   - Changes to `CLAUDE.md`, `docs/DESIGN.md`, `lib/allowed_sources.json`, `tests/jobs/allowed_sources_test.py`, `lib/fetch.py`, and anything under `.github/` (which govern repository permissions, data source whitelist, CI triggers, and secrets).

## Source & Licence Governance (`lib/allowed_sources.json`)
To keep the owner in control of external dependencies and copyright compliance, all external endpoints called by data jobs and scripts are strictly governed:
- **Owner-Merged Configuration:** `lib/allowed_sources.json` defines the approved whitelist of network hosts and allowed licences per source (e.g. Wikimedia: CC0, CC BY, CC BY-SA and public domain; GBIF: CC0 and CC BY only; read by `lib/licences.py`; GloBI: CC0, CC BY, CC-BY-SA, Public Domain; PAD-US: Public Domain). Both `lib/allowed_sources.json`, `tests/jobs/allowed_sources_test.py`, and `lib/fetch.py` are strictly owner-merged.
- **Runtime Guard (`lib/fetch.py`):** All external downloads and data pulls route through `lib/fetch.py`, which validates target hosts and scheme against `lib/allowed_sources.json` at run time and raises `PermissionError` on any unlisted host.
- **Automated Gate Enforcement:** The unit test `tests/jobs/allowed_sources_test.py` scans `jobs/*.py`, `lib/*.py`, `build/*.py`, and `jobs/*.sh` to verify every URL hostname is approved. It strictly forbids URLs dynamically built from variables (which could evade static inspection).
- **Modification Protocol:** Adding an external host or licence requires owner review and merge of `lib/allowed_sources.json`. Agents may optimize how existing allowed sources are used without modifying the list.
